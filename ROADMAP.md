## Closed (recent — for context)

- router.sock (C9, `plan-broker-and-sessions.md` §2, unit L-M1): relay's private, tokenless path into the relay-router, launched mode only. `internal/relay/launch.go`'s `Hello` now also captures relay's own kernel peer identity off the connecting end of its bridge dial (spike SP1: the connecting end's `LOCAL_PEERTOKEN` names the *accepting* process, confirmed empirically, not assumed) and cross-checks it against the OK reply's `relay_pid`, storing the result as `relay.RelayIdentity()`. `--router-socket` (default `{data-dir}/router.sock`, mode 0600) serves `RelayRouter.SocketHandler()` — the same dispatch as `--router-port` minus `/api/` and every `router.passthrough` `/<name>/` route (both would forward a caller's own upstream credential, which router.sock's caller never holds), and a `/v1/messages` narrowed to `router.anthropic.modelMap` targets only — behind `ListenSocket`'s per-connection admission check against `RelayIdentity()`. Every proxied response now carries `X-Relay-Model-Target`; `/v1/models` rows for a `modelMap` key carry a `target` field. After `RegisterManifest` succeeds, `RegisterModelHost` (`internal/relay/bridge_client.go`, tokenless, snake_case `service_id`/`router_socket`) registers the socket as relay's model-broker upstream; a refusal exits 78 (`relay.RegisterModelHostOrExit`), unlike `RegisterManifest`'s fail-open. `internal/peertoken` is a leaf-package copy of relay's own LOCAL_PEERTOKEN reader. `build.sh` now registers with `--capability model_host` alongside the existing two — see "process/infra" above for the live-box re-registration this still needs.
- 8181 (`--http-port`) resolved as read-only diagnostics: the anonymous TCP front now serves only an explicit allowlist (`GET /status`, `/status/status.css`, `/status/status.js`, `/api/status`, `/api/status/detailed`) via `internal/api.TCPDiagnosticsOnly` (`tcp_diagnostics.go`), applied only at the TCP listener's call site in `app.go` — the Unix socket keeps the full route table behind `bearerAuth`, unchanged. Everything else on TCP — every mutating route, `/ws`, terminal/session content, instance listings — answers a plain 404, identical to an unregistered path, so a probe can't tell "blocked" from "never existed". The allowlist was derived from what the dashboard's own JS calls (`status.js`'s only fetch is `GET /api/status/detailed`) plus its two static assets and the equally content-free `GET /api/status`; the dashboard has no action buttons, so nothing on it needed a mutating route restored. Path matching is exact method + exact path against an already-canonical form (`path.Clean` + a reject on any percent-encoded `/` in `RawPath`) rather than a prefix or pattern, so a request isn't normalized into an allowed one before the comparison runs. 8180 (`--router-port`) remains open — see production debt above. Relay passes a one-time 64-hex secret on fd 3 (`RELAY_LAUNCH_FD=3`); `relay.BootstrapLaunch` (`internal/relay/launch.go`) reads it before anything spawns, sends `Hello`, and relay binds the peer audit token as relayLLM's identity with the `manifest` + `projects` capabilities. Bridge requests carry no token; `relay.Launched()` is the "relay available" signal. `RELAY_SERVICE_TOKEN`, `RELAY_MCP_TOKEN` and `RELAY_FRONTEND_TOKEN` are removed and scrubbed from relayLLM's env and every child's; children get at most `RELAY_PROJECT_TOKEN`. Contract: `../spec-launch-identity.md`, `../relay/docs/launch-identity.md`.

- Package-layout refactor: relayLLM was one flat `package main` (106 files, ~40k lines) since it grew as a single service binary with no external consumers. Split into ~20 `internal/` packages along a dependency DAG (leaves: `types`, `clock`, `config`, `events`, `netutil`, `sshhost`; then `relay`, `permission`, `spawn`, `mcp`, `tools`, `servermanager`, `pioverlay`, `registry`; then `provider`; then `session`/`terminal`/`router`; then `api`; then `app`), with a thin `cmd/relayllm/main.go` calling `app.Main()`. `internal/testutil` holds the fakes (`FakeClock`, `FakeProvider`, `FakeMCPClient`, `FakeBridge`) every other package's tests import. Planned by Fable (verified against the actual code — five real import cycles found and their breaks identified — rather than guessed from file names), implemented by Sonnet as a sequence of git-committed, always-green migration steps (each ends with `go build ./... && go vet ./... && go test -race ./...` passing, plus the `-tags=live`/`-tags=llm` vet checks). No behavior change; this is a pure structural refactor. `build.sh`/`README.md`/`CLAUDE.md` updated for the new `go build -o relayllm ./cmd/relayllm` build path.
- `router.passthrough`: `/<name>/` routes that forward byte-for-byte, client credential included, to a fixed upstream. This is the OpenAI counterpart to the Anthropic passthrough. The live OpenAI traffic on this box is ChatGPT-subscription OAuth: OMP's `openai-codex` provider and the Codex CLI, both against `chatgpt.com/backend-api`. So the upstream is per-entry config rather than a hardcoded `api.openai.com`. Routing is by prefix, not by model field, because OpenAI's paths collide with the router's local ones. WebSocket upgrades pass through (OMP's codex transport prefers them), and `meteredResponseWriter.Hijack` counts their bytes. Measured first: Go's client reaches the codex backend over both SSE and WebSocket (JSON 401 without credentials, no Cloudflare challenge). No `modelMap`: redirecting a Codex model locally would need a Responses↔Chat translator plus WebSocket framing, and OMP/Codex already reach local models natively.
- Relay-router forwarded the inbound request path verbatim and ignored the upstream `BaseURL`'s path. A client on a bare base URL posts `/chat/completions` (llama.cpp mounts both `/X` and `/v1/X`, and Oh My Pi's `relay` provider uses `http://127.0.0.1:8180`). That kept working until europa moved to ExLlamaV3, which mounts `/v1` only. Measured: europa `/chat/completions` → 404, `/v1/chat/completions` → 200. So every OMP request to `relay/vCode` 404'd while `/v1/models` discovery still worked. `upstreamPath` (`relay_router.go`) now resolves `/v1/X` and bare OpenAI routes (`/chat/completions`, `/completions`, `/embeddings`, `/responses`) against the upstream's base path. That is the URL `provider_openai.go` already builds. Server-root routes such as llama.cpp's `/tokenize` still pass through unchanged. It also fixes base paths deeper than `/v1` (`…/api/v1`).
- Multi-interface bind support for `--router-bind`/`--http-bind`: both flags (and their env vars) now take a comma-separated list of addresses instead of exactly one, so relayLLM can listen on, say, a loopback address and one specific LAN IP without going all the way to `0.0.0.0`. Designed with input from Opus on the fan-out mechanism: one shared `*http.Server` per front, `Serve`d on N independently-bound `net.Listener`s (`listenAll` in `main.go`, `RelayRouter.Listen`/`Serve` replacing the old single-addr `ListenAndServe` in `relay_router.go`) rather than a custom multiplexing listener or N separate servers — the stdlib already supports one server serving many listeners, and `Shutdown`/`Close` on it tears all of them down at once, so multi-bind added zero new shutdown machinery. Binding each configured address is best-effort, not all-or-nothing: an address that fails to bind (port in use, no such interface, …) is logged and skipped rather than taking every other bind down with it — deliberately, per explicit direction after the first pass shipped fail-closed here (a configured address, e.g. a gateway IP, isn't guaranteed locally assignable in every deployment, so requiring every one to succeed would make its mere presence in the list a single point of failure). Only a total failure — every requested address rejected — surfaces as a startup error. The `router.anthropic` non-loopback+no-TLS startup guard now fails on *any* non-loopback bind in the list, naming the specific offender (`validateHTTPListener`'s own non-loopback+TLS guard was removed in a follow-up — see below). `routerOverlayHost` (the local pi subprocess's dial target) prefers a loopback bind over a LAN one when both are configured, since loopback can't be firewalled or DHCP'd away. `StartRelayRouter` gained an `error` return for the same reason `startMainTCPListener` already had one. `NewRelayRouter`'s ~60 test call sites were left untouched (single canonical `addr string`, unrelated to binding) to avoid touching every test in `relay_router_test.go`.

  **Follow-up (same day): `--http-port` lost its bearer-token requirement entirely.** Wiring `build.sh`'s service registration back up surfaced that `--http-port` (added for the status dashboard, see its own Closed entry below) required a bearer token while the sibling `--router-port` never has — an inconsistency nobody had asked for and the operator caught in review, not something flagged at build time. The token requirement, the `?token=` → `HttpOnly`/`SameSite=Strict` cookie bootstrap, and the non-loopback-without-TLS fail-closed startup guard were all removed for this listener; it's now served anonymously (`recoverMiddleware(mux)`, no `bearerAuth`), protected purely by which `--http-bind` addresses are actually bound — exactly `--router-port`'s existing posture, which is the whole point of this session's `--http-bind`/`--router-bind` multi-address work in the first place. `auth.go::bearerAuth` itself shrank to a single-carrier (`Authorization: Bearer`) check, since the cookie/query-param convenience it dropped existed solely to make a bearer-token-gated browser page usable, and the only listener left behind it (the Unix socket) is dialed exclusively by machine clients — relay's manifest-bridged dispatcher, the permission hook, direct socket clients — that were never using the cookie/query-param path to begin with. `validateHTTPListener` shrank to the ordinary cert/key pairing check; `--http-tls-cert`/`--http-tls-key` remain available as an opt-in transport-encryption knob with no forced-use guard, matching the router's TLS story. Net effect: `--http-bind 127.0.0.1,<lan-ip>` with no TLS cert now starts cleanly, same as `--router-bind` always could.

- Diagnostic status dashboard: `GET /status` (embedded HTML/CSS/JS, no build step) polling a new `GET /api/status/detailed` — open connections, throughput, idle/quiet/stalled state, models being served, virtual-model candidate reachability, and OpenAI-endpoint upstream availability, alongside the existing budgets/terminals. The relay-router's proxy path had zero connection instrumentation before this; a new `ProxyMetrics` registry (`status_metrics.go`) wraps the client `http.ResponseWriter` outermost — so the existing virtual-failover `virtualResponseRecorder` nests inside it — meaning a failed-over attempt contributes zero bytes and one connection row survives however many candidates were tried, with `defer`-based deregistration surviving the `http.ErrAbortHandler` panic a mid-stream backend failure raises. A two-bucket sliding-window rate estimator avoids the "long-frozen stream still reports a healthy average" failure mode a naive total/elapsed rate would have. Stall detection is deliberately asymmetric: a proxy connection mid-SSE-stream with no bytes for 60s (or a streaming request with no response at all for 180s, above the managed-server admission timeout so a queued cold-model load doesn't misreport) is a real bug signal, but a WebSocket viewer or chat session sitting idle between turns is normal and never flagged — conflating the two would make the dashboard cry wolf on every quiet devbox. `GET /api/status` (relay's Service Inspector) is untouched. Designed by Opus (backend instrumentation architecture) and Fable (visual/UX — the stalled-connection alarm treatment: inset border, solid ticking badge, glyph-only pulse disabled under `prefers-reduced-motion`, sparkline color-split at the stall boundary, document-title/favicon change for background tabs) in parallel, reconciled into one schema, then implemented by two Sonnet passes (backend, then frontend against the live endpoint) with independent verification at each stage. One real bug found in review after both implementer agents reported done and their own live-browser checks passed: every section's empty-state text (`setEmpty()` in `status.js`) toggled visibility but never replaced the placeholder "Loading…" string, so the common quiet-devbox case — the state the design explicitly called out as most important to get right — rendered as permanently stuck loading spinners instead of "No open connections" / "No managed models configured" / etc. across all six sections. Anthropic passthrough (`api.anthropic.com`, both the `/v1/messages` byte-for-byte branch and the raw `/api/*` catch-all Claude Code's OAuth bootstrap uses) is instrumented too — initially deferred as severable at design time, but explicitly requested as in-scope: every proxied route, Anthropic or otherwise, now shows up as a connection. **Follow-up landed:** the page turned out to be unreachable from an actual browser — it lives on the main mux, which bound only a Unix socket, while the one TCP port relayLLM listens on (`--router-port`) is a different mux whose catch-all answered `/status` with `{"error":"missing or invalid model field"}`; relay's front door is a socket only Eve dials, and Eve proxies only the `/api/*` + `/ws` routes it knows about. Fixed with `--http-port`/`--http-bind` (+ TLS pair), an opt-in second listener serving the *same handler value* as the socket — same routes, same `bearerAuth` — fail-closed on a non-loopback bind without TLS, and a true no-op when unset. Browser auth came with it: `?token=` is exchanged for an `HttpOnly`/`SameSite=Strict` cookie and redirected away, since a navigation can't send a header and the page's own `fetch` only inherits cookies. Deployed on the devbox as `--http-port 8181`, with the relay service record's `-url` pointing at `http://localhost:8181/status?token=…` so the tray links to it.
- Anthropic Messages API compatibility on the relay-router (`router.anthropic` in settings.json). Lets Claude Code point at relayLLM via `ANTHROPIC_BASE_URL`: real Claude models proxy through to `api.anthropic.com` byte-for-byte (headers, body, SSE — including the `/api/claude_cli/bootstrap` + `/api/hello` traffic Claude Code's own OAuth-mode UI depends on), and a config-driven `modelMap` redirects specific model ids to a local managed/virtual/endpoint model via a full Anthropic↔OpenAI translation layer (typed content blocks, tool_use/tool_result, streaming state machine with buffered tool-call blocks and a ping keepalive for Claude Code's idle-byte watchdog). Design input from reading the actual `claude` CLI binary found that Claude Code's model-list visibility for a subscription-OAuth login doesn't come from a discovery endpoint at all (it's explicitly skipped for that auth mode) — so no Anthropic-shaped `/v1/models` was built; visibility is a client-side `ANTHROPIC_CUSTOM_MODEL_OPTION` setting instead. One real bug caught by the test suite: `httputil.ReverseProxy`'s unconditional per-write `Flush()` call was reaching the real `http.ResponseWriter` even in non-streaming mode, implicitly sending a premature 200 before the aggregated response's real status was known.
- Virtual LLM failover (`virtual-llms` in settings.json): a stable model name with ordered fallback targets, resolved by the relay-router. Shipped, then hardened after `vCode` returned `400 unknown model` in the field. Three defects: endpoint reachability was treated as a hard gate on a cache that is 15s stale by design, so a healthy endpoint stayed unroutable after recovering; `ProxyRegistry.probe` inherited the inbound request's context, so a client disconnect recorded a false "offline" and poisoned that cache; and failover happened only at selection time, leaving remaining targets untried when one died mid-request. Reachability is now a preference ordering — believed-usable targets first, the rest as last-resort attempts — with retry on any failure that lands before the first response byte, a 3s dial cap so a black-holing host cannot eat 30s per candidate, and 503-naming-what-was-tried instead of `unknown model` for a name that is static config. Virtual rows now always appear in `/v1/models` and inherit `input_modalities` + `meta.n_ctx` from their first candidate.

- Virtual LLM failover, round two: hardening the ordering exposed a worse bug — mid-conversation failover permanently wedges the conversation. A production conversation had 97 turns on a llama.cpp endpoint and 8 on an oMLX endpoint (a spurious offline reading tripped failover, then failback); llama.cpp encodes reasoning as `content` + `encrypted_content`, oMLX as `summary` only, the client (Oh My Pi) replays the full reasoning history every turn, and `encrypted_content` is opaque and unrecoverable — so once the history contained an oMLX-shaped item, llama.cpp 400'd it (`item['content'] is not an array`) on every subsequent retry forever. Fix: conversation affinity. A pin keyed on `prompt_cache_key`/`user` (`relay_router_virtual_affinity.go`) now outranks reachability ordering once some target has served a conversation, recorded only on success, falling back cleanly if the pinned target is later removed from config. Bounded (1h TTL, 1024-entry LRU) and swept lazily like `ProxyRegistry`.

- Relay-router catalog rows now carry a top-level `context_length` alongside `meta.n_ctx`/`n_ctx_train`. Bug: `handleModels` only ever emitted context under `meta`, llama.cpp router mode's convention; a plain OpenAI-discovery client (confirmed against Oh My Pi's `lm-studio`/`openai-models-list` branch) reads a flat field instead and, finding none, silently substitutes a hardcoded 128K default. Measured effect: every model on this user's live router reported 128K regardless of its real `ctx-size` (e.g. 32768 for `Dolphin Mistral 24B RP`), which had already produced a live `request (39238 tokens) exceeds the available context size (32768 tokens)` failure. Fix is purely additive across all three row shapes — managed, endpoint, virtual — via one `resolveContextLength` helper, omitting the key entirely (never `0`) whenever no context figure is known.

- Router-level `reasoning_effort` rewrite (`router.reasoningEffortMap` in settings.json). Measured against a real llama.cpp server: `none` is accepted and turns reasoning off, `low`/`medium`/`high`/`xhigh` all work, but `minimal` 500s — and Oh My Pi's `--thinking off` has no wire value meaning "off" at all, clamping instead to the lowest entry in the model's configured `efforts` list (so it can be made to send `minimal` but never `none`), which sent one production client into a 150-request retry loop off a single prompt. The map rewrites `minimal` → `none` (or any other backend-specific pair an operator configures) on every proxied body — managed-alias, endpoint, and virtual-model routes alike — sharing one decode/encode pass with the existing model-field rewrite. Free-form string keys/values, not a hardcoded vocabulary; default off (absent/empty map) is byte-identical to before.

- Sibling knob `router.reasoningEffortTemplateKwargs` for the case the value swap above cannot fix: oMLX (`omlx/server.py:3594`) merges `request.reasoning_effort` verbatim into `chat_template_kwargs` and hands it to the model's Jinja template — no server-side semantics to rewrite. Measured against oMLX `CodeFast`: `reasoning_effort: "none"` had no effect (94 vs. 101 baseline chars of reasoning), while `chat_template_kwargs: {"enable_thinking": false}` turned it off (0 chars) on both oMLX and llama.cpp. The new map merges an object into `chat_template_kwargs` (creating it if absent, never overwriting a client-supplied key — mirrors oMLX's own `merged.setdefault(...)`) when `reasoning_effort` matches a configured key — matched against the client's *original* value, before `reasoningEffortMap` rewrites it, so the two knobs can be configured together off one source value. Values are arbitrary JSON, not just bools. Same opt-in shape and call sites as `reasoningEffortMap`; default off is byte-identical to before.

- Relay-router cold-start bug: `ProxyRegistry.LookupModel` only ever read the cache — `Snapshot` was the only thing that probed — so on a freshly started relayLLM the first chat request naming a live `endpoint/id` model 400'd with `unknown model` until some unrelated `/v1/models` call happened to warm the cache. Reproduced in production: a restart at 18:22:38, a `POST` for `omlx/CodeFast` at 18:22:46 rejected, then succeeding right after a catalog request. `LookupModel` now probes on a per-endpoint cache miss, reusing `Snapshot`'s existing TTL and single-flight rather than adding a second mechanism; an endpoint name that isn't configured still never probes. Virtual models were never affected (`candidatesForVirtual` already calls `Snapshot`). `relay_router_proxy_registry_test.go` pins the cold-start resolve, the no-probe-on-unconfigured-name guarantee, TTL-bounded no-reprobe-while-offline, reprobe-after-expiry, and single-flight under concurrency.

- Vision capability now reaches pi. Two independent gaps: the pi project overlay wrote bare `{"id": ...}` rows, and pi's `openai-completions` provider does no discovery — it gates image attachments on the model's `input` array (`model-config.js`), so every model read as text-only and pi answered "Current model does not support images" even for a model launched with an `mmproj`. The overlay now states `input: ["text"]` / `["text","image"]` explicitly. Separately, endpoint-backed rows in the router catalog carried no `architecture` key at all, which a client reading it unconditionally would choke on; they now do, populated from the upstream's own `architecture.input_modalities` when it declares one (llama.cpp router mode does). We never infer vision — an upstream that stays quiet reads as text, because sending images to a server that cannot take them fails mid-turn.

- Managed-server memory budget: `maxLoaded` + `maxMemoryGB` caps with LRU eviction, per-turn leases so eviction never lands mid-generation, and an idle reaper (`idleTimeoutMinutes`). Model sizes are computed from GGUF headers / MLX `config.json` — including sliding-window attention and per-layer GQA, without which Gemma 4 12B over-estimates ~25x. Session transports now resolve their backend per turn (`BackendResolver`), which also fixes sessions being pinned to a dead port after a server crash. New `gguf.go` + `server_memory.go`; budgets surfaced in `/api/status`.

- `mcp_client.go` `MCPManager` 0% → ~88% hermetic via the SDK's `NewInMemoryTransports` (real in-process MCP server). Extracted `newMCPClient()` so the test drives the production progress-notification handler. Subprocess `Start()` stays live-tier (`mcp_integration_test.go`). `mcp_client_test.go`.

Argv/env assembly extracted into pure builders (`buildClaudeArgs`/`buildClaudeEnv`/`buildPiArgs`/`resolveSkillDir`); the `bypassPermissions` / headless escape hatch is now asserted on the default tier. ## How to use this file

- Open items are grouped by priority within each section. Lower priority = lower expected ROI right now, not "less important."
- When you start an item, move it to **In flight**; add an owner if more than one person is working this repo.
- When you close an item, move it to **Closed** with a one-line note + ADR link for detail. Trim Closed periodically (keep ~10 entries).
- New items: state scope ("small/medium/large") and rationale (why it matters, what's the trigger).
- Cross-repo items stay here for visibility but are owned elsewhere — don't fix them in this repo.
